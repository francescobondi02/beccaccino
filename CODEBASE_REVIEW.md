# BECCA — Production Readiness Review

## 1. Verdict

**Not production-ready for a public launch today — but close.** BECCA is a *solid hobby-production* codebase sitting right at the edge of *professional production*. The engineering quality is genuinely well above what AI-generated code usually delivers: the concurrency model (a per-room async mutex plus a compare-and-swap on game start), the bot-service integration, the cross-language wire-format contract, the observability stack (pino redaction, request IDs, Sentry, health/ready split), and the operator-grade `RUNBOOK.md` are all things a senior team would keep as-is. There are no security holes, no data-loss paths, and authorization is enforced and re-checked at the resource level everywhere it matters. If the bar were "a well-built side project," this clears it comfortably.

What holds it back from "ship to real users tomorrow" is a small, concentrated set of high-severity defects — and two of them corrupt the one thing the whole product exists to compute: the score. The game-end threshold and winner are derived by summing only the `*Points` columns, silently discarding each round's figures (thirds), so in close games a team can fail to win when it actually has, or the wrong team can be declared the winner. Separately, round-end scoring reads the tricks with no `ORDER BY`, so the last-trick bonus and cricca bonus can be awarded to the wrong team on a path that runs at the end of *every* round. Account deletion is guaranteed to 500 for any user who has finished even one game (a data-rights problem), and the production Docker image prunes the Prisma CLI that its own boot command needs, making container startup depend on an unpinned network fetch. None of these are architectural rot — they are localized bugs with clear fixes.

Treat the four highs plus the `trust proxy` rate-limiter trap as pre-launch blockers: they are days of work, not weeks. The larger, non-blocking gap is that **no CI exists anywhere**, so the elaborate drift-prevention machinery this repo invested in (fixture parity tests, rules mirrors, the 409 legality gate) only works if a human remembers to run four separate test suites before every push to auto-deploy. Fix the blockers, then add CI to lock them in, and this crosses cleanly into professional-production territory.

## 2. What is already senior-quality

**Concurrency and state-safety.** `withRoomLock` (`backend/src/utils/roomLock.ts`) is a clean, correct per-room async mutex: it chains onto the tail promise, isolates a failed critical section from later waiters while still propagating the error to its own caller, and self-cleans idle map entries. It is applied at exactly the right check-then-act sites (set-briscola, play-card, ready-up), and the ready-up path pairs it with a conditional `updateMany({ where: { started: false } })` compare-and-swap so two simultaneous starts can't both fire. Lazy turn-timer recovery in `getGameState` re-arms timers and restores bot seats from the persisted `botModel` after a server restart — a real production safety net.

**Bot integration and the cross-language contract.** The bot HTTP path (`botClient.ts` + `turnTimer.playBotMove`) is defensively excellent: a 5s `AbortSignal` timeout well under the 60s turn budget, full shape-validation of the `/act` response before it can reach `playCard`, an `expected_legal_cards` cross-check, and distinct Sentry tags (`bot_fallback_to_autoplay` vs `auto_play_race`) so a fallback is never mistaken for the model. Bots deliberately do *not* arm the auto-play timeout or touch `timeoutCounts`, with a documented rationale (a slow bot can't be kicked and silently replaced). Drift between the TS serializer and the Python encoder is prevented by three composed layers — Python round-trip parity, committed byte-for-byte `(state, obs)` fixtures re-serialized by the backend (`botStateFixtures.test.ts`, which even guards its own fixture coverage), and the runtime 409 legality gate in `/act`. `botState.ts` documents and correctly implements the two non-obvious wire invariants (enum strings not indices; `raw = points*3 + figures`).

**Security and auth defaults.** Test-auth bypass is double-gated (`NODE_ENV=test` **and** `ALLOW_TEST_AUTH_BYPASS=true`) in both `index.ts` and `auth.ts`, so a misconfigured prod deploy can't disable auth. `playerId` is derived server-side from the JWT (anti-impersonation), the full-hands reveal is gated on `isPractice` server-side, bot accounts are created without a password, cookies are `httpOnly` + `secure`-in-prod with `sameSite` auto-switching, the socket buffer is capped at 10KB, and env validation fails fast (refusing to boot in prod without `FRONTEND_URL`).

**Observability and ops.** Structured pino logging with secret redaction (cookie/authorization/token/password), per-request correlation IDs, Sentry across handlers, a semantically correct `/health` (never DB-gated) vs `/ready` (probes the DB) split, graceful `prisma.$disconnect` on shutdown, and an exceptional `RUNBOOK.md` with concrete log queries, incident playbooks, and an honest "known caveats" section.

**Data layer.** All foreign keys were indexed in a dedicated migration matching the real join patterns; `deleteRoomAndPlay` deletes children-first inside a `$transaction` correctly compensating for the schema's `RESTRICT` FKs; `statsFilters.ts` centralizes the "practice/bot games never count" rule as shared `as const` filters so leaderboard/profile/metrics can't drift; seeded-RNG injection (`utils/random.ts`) makes shuffling and room-code generation deterministic in tests without polluting production.

**Frontend resilience.** A proper connect/reconnecting/disconnected state machine in `socketClient.ts` (infinite attempts with backoff, listener callbacks wrapped in try/catch); REST refetch-on-reconnect in both `GameRoom` and `GameTable` to recover events missed during a drop; disciplined stale-closure avoidance via `userIdRef`/`playersRef`; lazy-loaded routes behind `Suspense`; an `ErrorBoundary` reporting to Sentry with init gated on the env var; reconciled optimistic UI; `PlayingCard` image-load fallback; and `GameChat` capping stored messages. Socket-layer test coverage is real and behavioral.

**Build and deploy hygiene.** Multi-stage, non-root, health-checked backend Dockerfile with source-maps uploaded to Sentry then stripped; `vercel.json` ships sane security headers (`nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`), immutable asset caching, and an SPA rewrite that correctly excludes `/assets`; Vite `manualChunks` vendor split; conditional (no-op-on-local) sourcemap upload.

## 3. Findings

### Backend: game core

- **HIGH — Game-end threshold and winner drop per-round figures (thirds)** (`backend/src/services/gameService.ts:686`). The game-over check sums only `team0Points`/`team1Points` and never reads `team0Figures`/`team1Figures`; since per-round points are `floor(raw/3)`, `Σ floor(raw_i/3)` silently loses accumulated remainders (two rounds of 2 figures = a full lost point). This can prevent the game from ending when a team has truly reached `GAME_WIN_POINTS` and can flip the recomputed winner in close games. `botState.ts:195` and `CLAUDE.md` both do it the right way (`points*3 + figures`), so the game logic contradicts its own bot code. `getUserStats` and `getLeaderboard` repeat the lossy sum — fix by extracting one `cumulativeRealPoints(rounds)` helper (`raw = points*3 + figures`) and reusing it everywhere winners/thresholds are computed.
- **HIGH — Round-end scoring reads hands with no `ORDER BY`** (`backend/src/services/gameService.ts:572`). The `hand.findMany` orders each hand's *cards* but not the hands themselves, then `computePoints` awards the +3 last-trick bonus to `hands[length-1]` and the +3 cricca bonus to `allHands[0]`. Postgres does not guarantee row order without `ORDER BY`, and `Hand` rows are UPDATE-ed mid-round (`winnerId`), which can move tuples — so both bonuses can silently go to the wrong team at the end of every round. The author orders hands explicitly everywhere else (`botState.ts:84`), making this an oversight. Add `orderBy: { number: 'asc' }`.
- **MEDIUM — Caller/turn-order and game-winner logic duplicated across 3+ files** (`backend/src/services/gameService.ts:184`). The "round 1 = holder of quattro di denara; round N = `(prevCaller.seat+1)%4`" rule is implemented independently in `setupRound`, `setBriscolaUnlocked`, and `getGameState` (`gameController.ts:151`); the `(starterSeat+i)%4` play order is duplicated twice within `playCardUnlocked` (lines 448 and 526) and again in the controller; and the game winner is recomputed (via the lossy sum above) in three places and never persisted. A rules change or the figures fix must be made in every copy or the server disagrees with itself about whose turn it is. Extract `resolveCaller`, `seatOrder`, and `gameWinner` helpers and consider persisting the final winner on `GameRoom`.
- **MEDIUM — Kicked player re-emits `player_kicked_timeout` and runs a DB query every subsequent turn** (`backend/src/services/turnTimer.ts:373`). Once kicked, `executeAutoPlay` always increments the counter, so `currentCount >= 3` stays true and the kick block re-runs each auto-turn: re-adding to the kicked set, doing a `player.findFirst` join, and re-emitting the event. Clients get repeated "kicked" toasts and the server does a needless DB round-trip per auto-turn. Gate the emit/lookup on the transition into the kicked state (e.g. `currentCount === 3` or membership check).
- **MEDIUM — Timeout counter is pre-incremented and never reset on a real play** (`backend/src/services/turnTimer.ts:362`). `executeAutoPlay` increments `timeoutCounts` before it attempts to act, and the count is only cleared on whole-room teardown. A laggy player who plays every turn (including a T+59s REST play that races the fired timer) can accrue phantom timeouts and eventually hit the 3-timeout kick despite never abandoning a turn — harsher than the documented intent. Reset/decrement on a real move, increment only after a successful auto-play, and consider consecutive rather than lifetime counting.
- **LOW — `playableCards` throws a raw `TypeError` (500) in the briscola phase** (`backend/src/services/cardService.ts:65`). Line 59-60 guard with optional chaining but line 71 (`currentHand.cards`) does not, so a client fetching playable cards before briscola is chosen (no `Hand` row yet) gets a 500 with an internal error message. Return an empty array or a clean 4xx for this reachable, non-exceptional state.
- **LOW — Kicked-player auto-play timer is untracked, not `unref`'d, and uncancellable** (`backend/src/services/turnTimer.ts:85`). Unlike the bot and cleanup timers, this `setTimeout` isn't stored in `activeTimers` or `.unref()`-ed, so `clearTurnTimer` can't cancel it; after teardown a queued fire still runs once and re-creates a `timeoutCounts` map entry for the dead room (leaking one entry per torn-down room, since the sweep only iterates `activeTimers`). Track or `.unref()` it to match the other timers. Consistency nit, 500ms window.
- **LOW — `generateRoomCode` default length/charset drifts from docs and includes ambiguous glyphs** (`backend/src/utils/generateRoomCode.ts:3`). Default is `length = 6` over `A-Z0-9`, but `backend/CLAUDE.md` says "4-char uppercase" (doubly wrong), and the charset includes `0/O`, `1/I`, which is error-prone for the realistic "read the code to a friend" join flow. Align the doc and drop ambiguous characters.

### Backend: HTTP & security

- **HIGH — Account deletion always 500s for any user who has finished a game** (`backend/src/controllers/userController.ts:390-400`). `deleteCurrentUser` deletes `Player` rows only in non-started rooms, then hard-deletes the `User`; the comment claims "cascading will handle finished-game player records," but every FK is `ON DELETE RESTRICT` (`prisma/migrations/20251007114502_init/migration.sql:85`) with no cascade anywhere. Any user with one finished game retains `Player` rows, so `user.delete` throws an FK violation → caught → 500. Account deletion is broken for exactly the engaged users most likely to use it — a data-rights problem — and the comment guarantees the next maintainer trusts a cascade that doesn't exist. Anonymize/soft-delete finished-game rows (or add cascade) and add an integration test (register → finish a game → delete). It fails safe (no corruption), which is the only reason this isn't higher.
- **MEDIUM — Express `trust proxy` never enabled in production (pre-launch blocker)** (`backend/src/app.ts:56`). The only `app.set('trust proxy', …)` is `false` inside the test block; production never sets it, so `req.ip` (which the REST limiters key on) resolves to Render's load balancer, not the client. All HTTP clients collapse into one bucket and the 10/min auth limiter becomes global — modest concurrent login traffic trips 429 and locks legitimate users out. The socket layer already parses `X-Forwarded-For`, so the two layers disagree. Set `app.set('trust proxy', 1)` in non-test envs.
- **MEDIUM — `getGameState` is a ~240-line fat controller reimplementing service-layer game logic** (`backend/src/controllers/gameController.ts:109`). It inlines round-1 caller lookup, round-2+ rotation, whose-turn derivation, timer recovery, and score aggregation — logic `CLAUDE.md` assigns to `gameService`. The rendered turn indicator can silently drift from the authoritative play validation, and this is the hardest file in scope to test. Extract `getGameStateForUser`/`computeCurrentTurn` into the service.
- **MEDIUM — HTTP status codes derived by substring-matching `error.message`** (`backend/src/controllers/gameController.ts:42`). `chooseBriscola` and `handlePlayCard` both map `includes('not found')` → 404, `includes('not your turn')` → 403, etc. Rewording a message (or i18n) silently changes status codes, the table is duplicated across two handlers, and internal phrasing leaks to clients. Throw typed `GameError`s carrying a status/code and map on the discriminant.
- **MEDIUM — Inconsistent error handling: two handlers lack try/catch+Sentry, several leak raw messages** (`backend/src/controllers/gameController.ts:78`). `getGameState` and `getExitedRooms` (`roomController.ts:642`) have no try/catch, so a Prisma failure there loses the roomCode/userId breadcrumb every other handler adds (Express 5 still routes it to the global handler, so no crash). `getPlayableCards` returns `{ error: error.message }` and the briscola/play-card fallthroughs echo raw `message` — minor info disclosure. Wrap both handlers and return a generic 500 body.
- **MEDIUM — Registration username validation is weaker than profile update** (`backend/src/controllers/userController.ts:30`). `register` accepts any non-empty username; `updateCurrentUser` requires a trimmed length ≥ 3; neither caps maximum length. Usernames flow unsanitized to broadcast surfaces (`player_joined`, `chat_message`, leaderboard) — a 1-char, whitespace-padded, or multi-thousand-char username is an abuse vector (React escaping makes it display-abuse, not injection). Share one validator (trim, min 3, sane max, charset) between both paths.
- **LOW — Deprecated socket handlers `choose_team` / `set_ready` still mutate the DB outside the lock** (`backend/src/sockets/room.ts:129`). `choose_team`'s docstring claims it only errors, but it runs `player.update` and emits `team_chosen`; `set_ready` writes `isReady`. Both bypass `withRoomLock`. In practice no real client emits these (only integration tests do), and they still use JWT identity, so impact is near-zero — but the `choose_team` docstring actively lies, which is a maintenance trap. Delete them or make them match their docstrings.
- **LOW — Socket handlers are unbounded per connection except chat** (`backend/src/sockets/room.ts:56`). Only `send_chat_message` is rate-limited; `join_room`/`choose_team`/`set_ready` each run a `gameRoom.findUnique` with nested includes on every emit, and the per-IP cap limits connections, not events. An authenticated client can amplify cheap messages into expensive joined queries — a low-cost DoS surface against the single Postgres. Apply the chat limiter's shape to the DB-touching handlers.
- **LOW — Graceful shutdown doesn't drain in-flight requests or clear turn timers** (`backend/src/index.ts:159`). `server.close()` is non-blocking and its callback is never awaited, so `prisma.$disconnect()` + `process.exit(0)` run before open connections drain; per-room timers aren't cleared (only `stopMetrics`). On a Render SIGTERM redeploy a card play could hit a disconnected client. Mostly cosmetic at this scale — await a promisified `server.close()` with a timeout.
- **LOW — Dead code: unused `optionalAuth` export and a write-only `stores` map** (`backend/src/middleware/rateLimiter.ts:21`). `optionalAuth` (`auth.ts:75`) is exported but never imported; the module-level `stores` map is only written (its `storeId` is never consumed), while per-limiter cleanup uses the closure-local `store`. Flagged, not deleted, per the surgical-change rule — confirm with the owner before removing.

### Database

- **MEDIUM — No DB constraints back the per-round/room invariants; `joinRoom` can overfill a room** (`backend/prisma/schema.prisma:118`). Nothing enforces one Round per `(gameRoomId, number)`, one Hand per `(roundId, number)`, one PlayedCard per `(handId, position)`, or ≤4 players (the only `@@unique` is on nullable `seat`, so lobby joiners are all distinct). `joinRoom` does a check-then-act with no lock, so two concurrent joins can both read 3 and create a 5th player — `setupRound` then throws on `players.length !== 4` and the room can never start. The card-play invariants are guarded only by the in-process `withRoomLock`, which any horizontal scale-out bypasses. Add the three `@@unique` constraints as backstops and put `joinRoom` behind `withRoomLock`.
- **MEDIUM — Multi-row round writes are not transactional** (`backend/src/services/gameService.ts:146`). `setupRound` (create round → 4× `playerCard.createMany` → 4× seat `player.update`) and the round-end path (hand update → round update → gameRoom/next-round) run as separate statements with no `$transaction`, interleaved with socket emits; only `deleteRoomAndPlay` uses one. If `round.update` succeeds but `setupRound(next)` throws, the round is scored with no next round — `getGameState` re-arms a timer for an empty hand and the game is permanently stuck with the error swallowed by the lock chain. Wrap the deal/seat setup and the round-end + next-round creation in transactions, emitting sockets only after commit.
- **LOW — Non-transactional seat assignment plus register/create-room check-then-act races** (`backend/src/services/gameService.ts:127`). Seats are assigned with 4 individual `player.update` calls (not batched, half-assigned on mid-loop failure); `register` checks username/email then creates, so a concurrent duplicate surfaces as a generic 500 rather than 409; `createRoom`'s active-game check is also check-then-act. None corrupt data at current scale. Batch seats into the `setupRound` transaction and catch Prisma `P2002` → 409.
- **LOW — Migration hygiene, unindexed boolean filters, and O(all-games) in-memory leaderboard** (`backend/prisma/migrations/20251012175025_changed_a_bit/migration.sql:1`). The migration name carries zero audit info about a destructive `DROP COLUMN briscola`. `GameRoom.finished`/`isPractice`/`started` are filtered by leaderboard/rooms/metrics but unindexed, and `getLeaderboard` loads every ranked user's finished games and rounds into memory to aggregate in JS (with a `data: any` cache), slicing to top 50. All fine now (60s cache mitigates) — name migrations descriptively, type the cache, and revisit with a partial index or materialized standings beyond a few thousand games.

### Frontend: pages

- **MEDIUM — No API-client layer: raw `fetch` + credentials + error handling duplicated ~30 times** (`frontend/src/pages/Index.tsx:285`). All six pages hand-roll `fetch(`${API_URL}/…`, { credentials: 'include' })` with the same `res.ok`/`res.json()`/toast wiring (31 call sites), and the 409/`activeRoomCode` redirect block is copy-pasted verbatim four times. This is the single largest driver of the AI-built-vs-senior-team gap here; any convention change must be made in a dozen places. Add a thin `apiClient` (`api.get/post` injecting URL + credentials, throwing a typed `ApiError`) and one redirect helper.
- **MEDIUM — Auth-check logic reimplemented in all six pages instead of a shared hook** (`frontend/src/pages/GameTable.tsx:198`). Each page opens with a `GET /users/me` effect that sets username/userId and calls `setSentryUser`; the redirect-on-401 variant is copy-pasted across four of them (Index and Leaderboard intentionally swallow it, but nothing enforces that distinction). Extract `useAuth()` + a `RequireAuth` wrapper with Sentry tagging inside so it can't be forgotten on a new page.
- **MEDIUM — `GameTable` holds 33 `useState` slices** (`frontend/src/pages/GameTable.tsx:77`). Lines 77-158 declare 33 separate state slices, ~10 of which mutate together on every `refetchGameState`. State that always changes as a unit is the textbook `useReducer` case; 33 independent setters make the data flow hard to reason about and prone to inconsistent intermediate renders. Model round/hand/cards/points as one reducer fed by a `hydrate(serverState)` action.
- **MEDIUM — `GameTable` is 1160 lines with duplicated seat JSX** (`frontend/src/pages/GameTable.tsx:870`). The left/right/top seat blocks are near-identical (left and right are byte-identical but for positioning), and the connection banner is duplicated verbatim in `GameRoom`. A change to seat presentation must be made three times. Extract `<PlayerSeat>`, `<TableCenter>`, `<PlayerHand>`, and `<ConnectionBanner>`; combined with the hook extraction above, `GameTable` becomes a thin composition.
- **MEDIUM — Player normalization (with `any` cast) duplicated across pages** (`frontend/src/pages/GameRoom.tsx:88`). The `players.map((p: any) => ({ … username: p.user?.username ?? 'Sconosciuto' … }))` block appears twice in `GameRoom` and once in `GameTable`, each discarding type safety at the API boundary — a backend field rename produces no compile error, just runtime `undefined`. Define a typed `ApiPlayer` and one `normalizePlayer` in a shared module.
- **LOW — Two near-identical game-state hydration functions that have already drifted** (`frontend/src/pages/GameTable.tsx:353`). `fetchGameState` and `refetchGameState` set the same ~9 slices; the former accesses `data.round.briscola` unguarded while the latter uses `data.round?.briscola`, and only the refetch syncs the timer. Verifier note: the backend returns 404 when no current round exists and both paths gate on `res.ok`, so the unguarded access is not actually reachable — this is drift-prone duplication to collapse into one `hydrate()`, not a live crash.
- **LOW — Socket handler closes over stale `room`** (`frontend/src/pages/GameTable.tsx:588`). `handleAutoPlayed` reads `room?.players.find(...)` but the socket effect deliberately excludes `room` from its deps and registers once (when `room` is still null), so the auto-play toast always falls back to the literal "Giocatore." `playersRef` exists for exactly this and is used correctly elsewhere — read from it here. Cosmetic (a generic word in a transient toast), hence low.
- **LOW — Turn-timer countdown compares client clock to server clock** (`frontend/src/pages/GameTable.tsx:438`). The `turn_timer_started` handler stores the server's absolute `Date.now()` and the countdown computes `elapsed = Date.now() - serverTimestamp` on the *client's* clock, so clock skew corrupts the live countdown. The reconnect path already rebases correctly onto the client clock — apply one consistent formula. Display-only (server stays authoritative for auto-play), and real skew on NTP-synced browsers is usually seconds, so low.
- **LOW — `setTimeout` scheduled inside a `setState` updater** (`frontend/src/pages/GameTable.tsx:512`). The `setPlayedCards` updater schedules a refetch, so React 18 StrictMode double-invokes it in dev and fires two refetches. A parallel effect for the 4-card case already exists (lines 420-428) — mirror it. Harmless duplicate refetch today.
- **LOW — `onGameStarted` schedules a hardcoded 5s navigate with no cleanup** (`frontend/src/pages/GameRoom.tsx:287`). The cleanup calls `offGameStarted()` but never clears the `setTimeout`, so leaving the room within the 5s window still fires `navigate('/game/…')`, pulling the user into a game they left; the `5000` also violates the named-constant rule. Store and clear the timeout id; hoist the constant.
- **LOW — Dead `isAuthenticated` state in `GameTable` and `GameRoom`** (`frontend/src/pages/GameTable.tsx:79`). Declared and set but never read in either file (they gate via redirect-on-401, not this flag); `turnTimer.phase` is likewise written but never rendered. Dead state misleads readers into thinking gating exists here — remove it.
- **LOW — `handleJoinRoom` and `handleJoinByCode` are near-duplicate functions** (`frontend/src/pages/Index.tsx:356`). Identical but for reading/trimming `roomCode` from state and an empty-input guard; both POST `/rooms/join` with the same 409 block, toasts, and navigate. Have `handleJoinByCode` validate then delegate to `handleJoinRoom(roomCode.trim())`.
- **LOW — `handleLogout` duplicated across four pages** (`frontend/src/pages/Profile.tsx:170`). Index, GameRoom, Profile, and Leaderboard each define a `handleLogout` that POSTs `/users/logout`, clears Sentry, and toasts, differing only trivially. Move it to the proposed `useAuth()` hook or a single `logout()` helper.

### Frontend: infrastructure

- **MEDIUM — Socket event names/payloads are hand-mirrored on both sides with no shared contract** (`frontend/src/sockets/roomHandlers.ts:22`). The backend emits ~21 events, each re-declared by hand on the frontend with an inline payload type; there is no shared types package. Drift already exists — the backend emits `team_chosen`/`ready_changed` with a `playerId` field the frontend types omit. Renaming an event or reshaping a payload produces no compile error and fails silently at runtime — the largest drift surface in the app. Extract a shared `events.ts` (name constants + payload interfaces) or type `getSocket()` with `ServerToClientEvents`/`ClientToServerEvents` generics.
- **MEDIUM — Server-emitted `error` events are never surfaced to the user** (`frontend/src/sockets/lobbyHandlers.ts:88`). The backend emits `socket.emit("error", { message })` for many failure paths ("Team is full," "Too many messages," etc.); the only frontend listener just `console.error`s it, and neither `GameRoom` nor `GameTable` registers an `error` listener at all. A player whose socket action fails gets zero feedback — the UI just appears to do nothing. Register one `error` handler that surfaces `data.message` via the existing `toast.error`.
- **MEDIUM — Header links to `/settings`, a route that does not exist** (`frontend/src/components/Header.tsx:79`). The account dropdown navigates to `/settings`, but `App.tsx` defines no such route, so every logged-in user who clicks "Impostazioni" lands on the 404 page. A visibly broken nav item reads as unfinished — add the page or remove the item.
- **MEDIUM — `GameTable.tsx` (the core game UI, ~1160 lines) has no unit tests** (`frontend/src/pages/GameTable.tsx:467`). Tests exist for the socket handlers and leaf components but none reference `GameTable`, which owns the riskiest logic: optimistic card removal, the `<4`-vs-4-card refetch branch, signal-clear-on-new-trick, and server-timestamp timer sync — exercised only by the happy-path Playwright e2e. Extract the pure-ish reducers and add focused unit tests. Coverage gap, not a bug.
- **MEDIUM — Two divergent listener registries; the lobby side leaks callbacks after unmount** (`frontend/src/sockets/lobbyHandlers.ts:30`). `lobbyHandlers` exposes only `on*` (no `off*`) and resets all callback arrays on every register, so `Index`'s callbacks are never explicitly removed on unmount (masked only because the next register clears them); `roomHandlers` uses the opposite convention (per-callback `off*` removed symmetrically in cleanup), and `onGameStarted` is a third shape (a single nullable slot). Two files solving one problem with opposite conventions will confuse the next change. Pick one pattern — ideally `register*` returning an unsubscribe. Latent (no current user-facing bug).
- **LOW — Auth-failed sockets retry forever with no re-login prompt** (`frontend/src/sockets/socketClient.ts:69`). `reconnectionAttempts: Infinity` plus a `connect_error` handler that only `console.error`s means a token that expires mid-session leaves the socket in a perpetual "Riconnessione in corso…" state with no prompt to re-authenticate. Largely mitigated on mount (protected pages REST-check `/users/me` and redirect on 401), so the real trigger is expiry on a long-open tab. Detect auth-class `connect_error` and surface it / cap attempts.
- **LOW — `GameTable` refetches on the initial socket connect, unlike `GameRoom` which guards against it** (`frontend/src/pages/GameTable.tsx:452`). `GameRoom` skips the first connect via an `isInitialConnect` flag; `GameTable` doesn't, so a cold mount fetches twice. Minor redundant call and an inconsistency between two pages solving the identical problem — apply the same guard or factor into a shared hook.
- **LOW — `RoundEndDialog` accepts `team0Figures`/`team1Figures` props it never renders** (`frontend/src/components/RoundEndDialog.tsx:18`). The figures values are passed in from `round_ended` but the body only renders points — given that figures are a distinct scoring remainder, this is likely an incomplete feature (the round summary omits the figure count players expect). Render them or remove the props.
- **LOW — `VITE_API_URL` is read with no fallback or validation in 6 files** (`frontend/src/components/AuthDialog.tsx:22`). `socketClient.ts` has a dev fallback but the REST consumers do not, so an unset var in a deploy produces confusing `undefined/users/login` fetches rather than a clear error. Centralize env access in one `config.ts` that validates at startup.
- **LOW — `getConnectionStatus()` mutates module state as a side effect of a read** (`frontend/src/sockets/socketClient.ts:81`). The getter reassigns `connectionStatus = "connected"` when it detects a stale tracked value — a pure-looking read performs a hidden write. Fix the transitions so the value can't go stale (seed from `socket.connected`) and keep the getter pure.

### DevOps & cross-language contracts

- **HIGH — Dockerfile prunes the Prisma CLI but the boot CMD runs `npx prisma migrate deploy`** (`backend/Dockerfile:55`). `npm prune --omit=dev` removes `prisma` (a devDependency; only `@prisma/client` is a runtime dep), so at container start `node_modules/.bin/prisma` is gone and `npx` fetches an *unpinned* CLI from the registry at every boot. The documented critical startup path now depends on outbound network at boot and can pull a CLI major that diverges from the pinned `@prisma/client 6.16.3`; a registry hiccup means the container never starts. Move `prisma` to dependencies (or don't prune it) so the boot uses the locally installed, version-locked CLI.
- **MEDIUM — No CI anywhere: the entire drift-prevention strategy is unenforced** (`DEVELOPMENT.md:34`). No `.github` or CI config exists in the superproject or any submodule, yet the repo invests heavily in guards that only fire if run manually — backend unit+integration Jest, frontend Vitest, Python `pytest` rules parity, the byte-for-byte `botStateFixtures.test.ts`, and the `gen_bot_fixtures` no-op requirement. Because backend/frontend/ai are independent submodules that auto-deploy on push, a contract-breaking change can ship to prod with green local intuition and no signal. Add minimal per-submodule GitHub Actions gating merge, plus one cross-cutting job that runs `gen_bot_fixtures` and fails on any git diff. This is the linchpin — do it right after the blockers so CI goes green on a fixed tree.
- **MEDIUM — `docker-compose` backend service cannot start as documented** (`docker-compose.yml:34`). The service sets only `DATABASE_URL=…@db:5432`; `prisma migrate deploy` uses `DIRECT_URL`, whose only source is the volume-mounted `backend/.env` with a `localhost:5432` value that is unreachable inside the container (localhost is the container, not the `db` service) — so a fresh-clone `docker compose up` dies on the migration (or, with no `.env`, on schema validation). Verifier note: the volume mount does supply `JWT_SECRET`, so the "jwt.ts throws" half of the original claim is inaccurate; the `DIRECT_URL`/localhost failure is real. Give the compose service `DIRECT_URL=…@db:5432` (and `FRONTEND_URL`), or drop the backend service and document the host-backend topology `setup.sh` already favors.
- **MEDIUM — Frontend production build does no type-checking, with strict mode off** (`frontend/package.json:8`). `"build": "vite build"` transpiles per-file without type-checking and there is no `typecheck` script; `tsconfig` sets `strict: false` and `strictNullChecks: false`. Combined with no CI, type errors and null-deref bugs ship straight to Vercel — precisely where `GameTable`'s dense socket-driven state hides them. Add `"typecheck": "tsc --noEmit"`, chain or CI-gate it, and enable `strictNullChecks` incrementally.
- **LOW — Committed `.env.e2e` contains a real 64-char hex JWT secret** (`backend/.env.e2e:4`). It is a genuine high-entropy secret (not a placeholder), now permanent in git history. Verifier note: it is dev/local-only (`NODE_ENV=development`, localhost DB) and *is* referenced (`frontend/DEVELOPMENT.md:130`), so it is not the prod secret and not dead — rotation isn't required, but scrub the value to an obvious placeholder and `.gitignore` it.
- **LOW — Cross-repo fixture path couples the backend integration test to the monorepo layout** (`backend/tests/integration/botStateFixtures.test.ts:13`). The test reads `../../../ai/serving/fixtures/bot_states.json` (the sibling `ai` submodule) eagerly at collection time, so a standalone clone of the backend repo (which is how Render deploys it) or submodule-level CI throws a missing-file error with no explanation. Guard with `describe.skip` + a clear message when the fixture is absent, and document the monorepo requirement.
- **LOW — Frontend tracks two lockfiles** (`frontend/package.json:1`). Both `package-lock.json` (2026-05-31) and a ~7.5-month-stale `bun.lockb` (2025-10-14) are committed, though the toolchain is npm everywhere and there is no CI to catch a divergent tree. Delete the stale `bun.lockb` and `.gitignore` it; keep exactly one source of dependency truth.
